# 前端开发规范

本规范适用于 `frontend/`。目标是让页面代码容易定位、接口契约清晰、异步行为可控，而不是追求目录数量或形式上的抽象。

## 1. 当前技术边界

- 使用 React、TypeScript、React Router、Ant Design、SCSS 和 ECharts。
- 业务页面和业务组件默认使用 CSS Modules（`*.module.scss`）；普通 `.scss` 只用于真正的全局样式。
- 保持 TypeScript `strict`，不通过 `any`、连续类型断言或非空断言掩盖接口问题。
- 当前不引入 Redux、RTK Query、Vitest、React Testing Library 或 MSW，除非后续需求明确需要。
- 普通页面优先使用 React 原生状态；复杂流程使用 reducer 表达显式状态转换。
- ECharts 等大模块继续按需加载，不要重新打入首屏同步依赖。
- 前端 Dockerfile、Nginx 配置集中在 `frontend/build/`；Vite 配置 `vite.config.ts`、包清单、锁文件、TypeScript 配置和 HTML 入口保留在 `frontend/` 根目录，使用工具默认入口。
- `dist/`、依赖目录、增量缓存和本地环境文件不提交。构建使用 `tsc --noEmit`，并检查未使用的变量、参数及副作用导入。

## 2. 目录与职责

页面模块可按以下结构组织，但只创建实际需要的目录：

```text
pages/<Page>/
  <Page>Page.tsx        页面组合、路由参数和页面级 UI 状态
  <Page>Page.module.scss 页面或业务模块的局部样式
  components/           有明确视觉或交互职责的子组件
  hooks/                需要 React 生命周期的复杂副作用
  model/                页面状态类型、reducer、选择器和纯状态转换
```

- `src/api/client.ts` 只处理通用 HTTP 能力，例如同源前缀、Cookie 和统一错误。
- 后端资源接口按领域放入 `src/api`，例如会话、配置、收藏、反馈和音频；页面不得直接拼接 URL 或调用 `fetch`。
- 接口传输和协议解析统一放在 `src/api/`，默认不创建页面内部的 `api/` 目录，不保留同一接口的多套请求函数。
- 简单请求与响应类型跟随对应 API 文件导出，例如认证在 `api/auth.ts`、会话在 `api/conversations.ts`、配置和目录在 `api/workbench.ts`、常见问题和收藏在 `api/questions.ts`。消费者使用 `import type`，不通过无意义的别名或中转导出隐藏类型来源。
- 多个模块共用的复杂类型可以独立存放，例如 `models/ask.ts` 仅保留查询计划、结果和分析步骤。页面状态及展示层派生类型留在对应页面的 `model/` 或组件内，不混入接口契约。
- 跨页面真正共享的能力才提升到 `src/api`、`src/models`、`src/lib` 或公共组件目录。
- 不为了“以后可能复用”提前创建公共抽象。

## 3. `.tsx`、Hook、普通 `.ts` 的判断

“是否复用”不是唯一判断标准，按职责选择位置。

放在对应 `.tsx` 中：

- 弹窗、Popover、折叠、Tab、图表视图等局部 UI 状态。
- 只服务当前组件的简单格式化和点击处理。
- 不涉及请求竞态、订阅或资源释放的短小逻辑。

放在独立 Hook 中：

- 使用多个 React 生命周期，并需要统一清理。
- 管理 `AbortController`、MediaRecorder、Audio、ResizeObserver 等外部资源。
- 管理请求竞态、流式会话或多个相关状态，内联后会遮蔽组件结构。
- Hook 即使只有一个调用方也可以存在，但必须有独立、清晰的职责；禁止创建只包装一行状态的 Hook。

放在普通 `.ts` 中：

- NDJSON 解析、数据转换、格式化、校验等不依赖 React 的逻辑。
- reducer、状态机和纯业务规则。
- API 请求函数和传输协议。

页面组件只负责组合。如果一个页面同时包含完整请求流程、媒体生命周期、列表变更和大量 JSX，应先拆出领域逻辑，而不是继续增加页面内函数。

## 4. 接口规范

- API 函数名使用动作和领域对象，例如 `fetchConversation`、`createConversation`、`submitFeedback`。
- 请求路径只出现在 API 层；组件接收数据和语义化回调。
- 不假定不同查询类型拥有相同字段。后端可能只在指标结果返回 `rows`，只在基础资料结果返回 `records` 和 `record_columns`。
- 对真实可选字段使用可选类型和明确默认值，不用强制断言伪造完整性。
- 后端错误优先展示安全的 `detail`；无法解析时使用稳定的用户提示，不展示原始响应或凭据。
- 修改后端响应结构时，必须同步更新前端类型、所有消费位置和验证步骤。

### 普通 JSON 请求

- 使用通用 `request`/`post` 封装。
- 页面加载请求应防止卸载后的状态写入。
- 多个独立资源可以并行加载；不要无故串行等待。
- 设置等可编辑页面必须先成功加载后端配置再展示编辑表单；失败时提供明确错误和重试，禁止把前端硬编码配置伪装成已保存配置。

### NDJSON 流

- 流解析必须在独立 API/service 函数中完成，不让组件直接操作 `ReadableStream`。
- 正确处理跨 chunk 的半行数据、最后一个无换行事件、空行、非 2xx 响应和缺失响应体。
- UI 只消费有类型的 `status`、`analysis`、`result` 事件。
- 流结束但没有 `result` 时必须视为不完整响应，不得默认为成功。

## 5. 状态和异步流程

- 复杂流程使用明确状态，例如 `idle → creating → streaming → cancelling → idle`。
- 不用多个可能互相矛盾的布尔值表达同一个流程。
- 会话加载和流式生成必须支持取消，并使用请求版本或 request ID 防止旧响应覆盖新页面。
- URL 中的会话 ID、当前会话状态和页面内容必须保持一致。
- 乐观消息必须有稳定的临时 ID；服务端消息到达后不得造成重复展示。
- 切换会话时应中止或隔离旧请求，不能让旧会话结果写入新会话。
- `finally` 中只清理由当前请求持有的状态，避免旧请求清除新请求的 loading/busy 状态。

## 6. 组件拆分

按职责和变化原因拆分，不按固定行数机械拆分。

适合拆成组件：

- 有独立视觉区域，如输入器、消息、结果卡、数据目录。
- 有自己的交互状态或资源生命周期。
- 有清晰、稳定的输入输出接口。
- 父组件需要理解大量实现细节才能渲染该区域。

不适合拆分：

- 只有一层无语义包装。
- Props 几乎复制父组件所有状态。
- 子组件仍通过大 Context 隐式读取整个页面控制器。
- 只是为了减少文件行数，却增加跳转成本。

Props 应表达业务语义：

- 使用 `onAsk(question)`，不要向子组件传整个 session/controller。
- 使用精确类型，避免 `Record<string, any>` 和 `Function`。
- 回调命名使用 `onXxx`，内部处理函数使用 `handleXxx`。
- 组件不得修改不属于自身职责的数据源。

## 7. 样式规范

- 新增或重写的业务页面、业务组件默认使用 `*.module.scss`，在 TSX 中通过 `styles.xxx` 或 `styles["xxx"]` 引用，不使用字符串形式的全局类名。
- 同一业务模块可以先共享一个页面级 Module 文件；只有组件样式具备独立职责、规模明显增长或需要跨处复用时，才拆成组件同名的 `*.module.scss`，避免产生大量零散小文件。
- Layout 及其只服务于该 Layout 的 Header、Menu 等子组件可以放在同一目录并共享一个 CSS Module，响应式状态由该布局模块统一维护。
- `global.scss`、reset、字体声明、设计令牌和确实作用于整个应用的规则可以保留普通 `.scss`；不得把业务页面选择器放入全局样式。
- CSS Modules 内的类名应表达业务或组件语义。现有 BEM 命名可保留；新代码无需为了隔离而重复冗长页面前缀，因为构建会生成局部作用域。
- 组件状态使用 `is-*` 或 `data-*`，例如 `is-ready`、`data-status="running"`。
- 页面专属的 Ant Design 覆盖必须从本地类向下书写，并用 `:global(...)` 显式标记库类，例如 `.toolbar :global(.ant-btn)`。只有明确适用于全站的排版规则可以放入 `styles/overrides.scss`，并写明用途；目前仅保留表格等宽数字，禁止在其中放置业务页面或抽屉专属样式。
- 颜色、间距和圆角在同一页面保持有限集合；相同语义不要出现多组近似值。
- 响应式规则与对应模块样式放在一起。布局外壳留在 `layouts/WorkspaceLayout/`；全局样式及跨页面共享的局部样式放在 `src/styles/`。例如 `management.module.scss` 服务于设置、反馈内容区，仍然使用 CSS Modules，不是全局样式。
- 不用内联 style 实现稳定视觉规则；运行时计算的尺寸或图表配置除外。
- 文本可能变长的区域需要考虑截断、换行和窄屏，不用固定文案长度推断布局。
- 数量、表数、日期、模型状态等动态内容必须来自数据，不写死在 CSS 或 JSX。

## 8. Ask 页面专项约束

- `/ask` 的后端接口和 NDJSON 协议默认保持兼容；未获授权不要修改后端。
- 实时分析过程展示后端实际发送的步骤，不生成或伪造模型思维链。
- 回答等待期间使用简洁的“正在思考”，不展开实时分析面板。提示组由后端真实阶段（理解问题、执行取数、整理结果）选择，组内每 2.4 秒轮换一句并淡入；阶段变化时从首句开始，未知阶段使用通用提示。轮播不表示操作已完成；回答完成后仍可查看后端返回的分析过程。完成、失败、取消或切换会话时必须清理轮播计时器。
- 指标查询和基础资料查询必须走不同的结果分支，并允许各自专属字段缺失。
- 停止生成需要中止浏览器请求并恢复可输入状态。
- 历史会话、连续追问、收藏、常见问题、反馈、语音、导出和图表切换是现有功能，重构时不得静默丢失。
- 结果数值和图表必须来自同一响应结果，不在前端重新计算业务指标。
- 数据截止日期、可查询范围和业务口径以 catalog/result 为准。

## 9. 开发流程

1. 查看 `git status`，识别用户已有修改。
2. 阅读入口、调用方、类型和对应后端接口，先确认真实契约。
3. 明确改动属于组件、Hook、model 还是 API 层。
4. 完成实现后运行 `cd frontend && npm run format:check && npm run build`。格式规则以 `frontend/.prettierrc.json` 为准；需要整理时运行 `npm run format`，只影响前端，忽略依赖、构建产物、锁文件和本地环境文件。日常修改优先只格式化涉及的文件。
5. 使用现有本地后端验证受影响流程；流式功能至少观察真实事件和最终结果。
6. 检查浏览器控制台和页面空白、滚动、窄屏、长文本等视觉问题。
7. 删除替代后的旧入口、死代码和失效样式引用。
8. 交付时说明改动、验证范围和仍存在的警告。

当前没有前端自动化测试框架。不要仅为了单次改动新增测试技术栈；若未来引入，应先说明维护成本和要覆盖的风险。

## 10. 禁止的反模式

- 一个 controller 暴露整个页面状态，再通过大 Context 供所有组件任意读取。
- 在组件 `useEffect` 中重复实现 API、错误解析和 NDJSON 解析。
- 使用 `busy`、`loading`、`sending` 等多个布尔值表达互斥状态却没有统一状态机。
- 用硬编码数量或文案代替接口中的 catalog/settings 数据。
- 为消除 TypeScript 报错把响应整体断言为目标类型。
- 新旧页面并行挂在同一路由，或保留已替换模块的全局样式。
- 为新业务页面新增普通 `.scss`，或在 CSS Module 中通过 `:global` 暴露业务类名。
- 未验证真实响应就根据类型定义假设字段始终存在。
