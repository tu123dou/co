# 业务表设计评审

评审日期：2026-09-12

评审范围：`analytics` schema 的 13 张业务表。应用、会话和 pgvector 表不属于本次业务模型评审。

## 结论

现有模型的核心账务链路设计合理，可以继续使用：

```text
contracts → contract_items → revenue_entries / cost_entries
         └───────────────→ payment_entries

monthly_targets 独立于合同事实
```

合同、收入、成本、回款和目标采用不同事实粒度，查询时分别聚合，能够避免多事实直接连接造成金额重复。现有数据库中的金额与日期一致性检查也全部通过。

该模型已按算力产品与解决方案销售场景完成 5 处调整，另外有 4 处可以后续处理。

## 必须调整

### 1. 经营组织不能强制绑定城市

当前 `org_units` 要求每个组织都有 `region` 和 `city`，适合代表处，不适合渠道部、金融系统部、泛政府系统部等跨地区组织。

调整建议：

- 增加稳定的 `code` 和 `unit_type`。
- 保留 `parent_id` 表达中国区、区域、系统部、代表处层级。
- `region`、`city` 改为可空；只有地域型经营单元填写。

### 2. 合同只保留一个客户

第一版只保留单一合同客户。`contracts.customer_id` 统一表示合同经营分析使用的客户，客户与行业查询都沿用这一个字段。这样可以缩短查询路径并避免模型混淆客户口径；接入真实 CRM 后再根据明确的数据来源评估是否扩展多参与方模型。

### 3. 维表缺少稳定业务编码

组织、行业、客户、产品线、产品和销售人员目前主要依赖自增 ID 和名称。接真实 CRM、ERP 或 Excel 台账时，名称会存在简称、重名和改名，无法稳定增量同步。

调整建议：

- 为 `org_units`、`industries`、`customers`、`product_lines`、`products`、`salespeople` 增加唯一业务编码 `code`。
- 自增 `id` 继续作为数据库代理键，业务编码负责源数据匹配。
- 第一版不提前绑定某个具体源系统的外部 ID。

### 4. 硬件合同明细缺少数量和税务字段

`contract_items` 目前只有产品和不含税金额，无法回答产品台套数、平均单价、含税合同额，也无法解释不同产品的税率。

调整建议：

- 增加 `quantity`、`unit_name`、`tax_rate`、`amount_with_tax`。
- 保留 `amount_ex_tax` 作为问数和经营分析的统一金额口径。
- 数据库约束数量大于 0、税率大于等于 0、金额大于等于 0。

### 5. 目标表缺少保底和滚动预测

`monthly_targets.revenue_target` 只能表达收入目标，不能回答 demo 中的保底和滚动预测问题。

调整建议：

- 保持现有“月份 × 经营单元 × 产品线”粒度不变。
- 增加 `floor_amount` 和 `forecast_amount` 两列。
- 第一版只管理收入目标与预测，不提前引入多指标、多场景模型。

这种列式设计的扩展性略低，但查询路径最短，也更符合当前固定的三个业务口径。将来确实出现签约目标、订货目标等多类目标时，再迁移到通用目标场景模型。

## 演示场景新增的一张表

`receivable_entries` 是未回款、逾期应收和单笔应收计划排行的基础。第一版聚焦已经签约后的经营与财务分析，不保存签约前商机，因此删除了 `opportunities` 以及合同上的商机引用。当前业务表为 13 张，全库领域表为 27 张。

## 查询复杂度控制

每类指标固定一个事实入口，模型只选择指标和维度，程序负责使用预定义连接：

| 问题类型 | 事实入口 | 主要连接路径 |
|---|---|---|
| 确认收入、成本、毛利 | 收入/成本记录 | 事实 → 合同明细 → 合同 → 组织/客户；产品维度再连接产品 |
| 签约额 | 合同明细 | 合同明细 → 合同 → 组织/客户/产品 |
| 回款额 | 回款记录 | 回款 → 合同 → 组织/客户，不提供产品线拆分 |
| 目标、保底、预测、达成率 | 月度目标 | 目标 → 组织/产品线；与收入分别汇总后计算比率 |
| 应收、逾期、账龄 | 应收计划 | 应收 → 合同 → 组织/客户 |

不建立任意表自动探索或让模型自行拼接连接。新增指标必须在语义层登记固定事实、日期字段、允许维度和连接模板，从而降低错表、错字段和重复累计的风险。

## 建议调整，但不阻塞第一版

### 1. 状态字段约束

`contracts.status` 当前只要求非空，数据库可写入任意字符串。第一版可以增加 CHECK 约束，后续状态经常变化时再改成状态字典表。无需为了状态单独建表。

### 2. 外键索引

PostgreSQL 不会自动为外键引用列建立索引。当前 2 万级事实数据没有性能问题；接入大数据量后，应根据查询计划补充 `contracts.org_unit_id`、`contract_items.product_id`、`customers.industry_id` 等索引。索引应经过 `EXPLAIN ANALYZE` 验证，不需要现在把所有外键都机械建索引。

### 3. 历史维度变化

客户行业、产品线归属变更后，历史报表目前会随维表变化。演示数据不会修改这些归属，因此第一版不做缓慢变化维。接真实数仓时再根据源系统历史能力决定采用 SCD2 或事实快照。

### 4. 回款金额口径

当前 `payment_entries.amount_ex_tax` 是管理口径的不含税折算回款。真实银行流水通常是含税实收金额。第一版继续使用当前字段并明确口径；接财务系统时再同时保存原币实收、币种和管理折算金额。

## 可以保持不动

- `contracts` 与 `contract_items` 分离正确，一份合同可以包含多个产品。
- `revenue_entries` 按合同明细分期确认正确，支持产品线收入分析。
- `cost_entries` 独立于收入事实正确，毛利查询应分别聚合后计算。
- `payment_entries` 保持合同粒度是合理的；没有可靠分摊规则时不应伪造产品线回款。
- `industries`、`product_lines` 单独建维表合理，无需合并到客户或产品表。
- 金额采用 `NUMERIC(18,2)` 合理。
- 日期采用 `DATE` 合理，当前经营分析不需要精确到秒。
- 分析业务表与 `app` 应用表分 schema 隔离合理。

## 数据库实查结果

以下检查均为 0 条异常：

- 合同经营单元与销售人员经营单元不一致。
- 月度目标日期不是月初。
- 收入、成本或回款早于合同签约日期。
- 合同明细累计确认收入超过签约金额。
- 合同累计回款超过签约金额。
- 同一产品线内存在重名产品。

这说明现有数据生成器在原模型下保持一致；后续改造需要继续保留并扩展这些检查。
